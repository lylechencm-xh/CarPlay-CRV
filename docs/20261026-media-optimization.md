# 2026-10-26 媒体处理与诊断优化

本次针对 `_carlogs/20261026/日志深度分析.md` 落实代码改动。未将早间计算成本升高认定为已解决，也未替换加密算法、扩大音频延迟预算或改变视频参考链策略。

## 已实现

- 音频接收使用有界、按实际包长度匹配的缓冲复用。UDP 接收缓冲仍复制一次以隔离生产者与消费者；没有原始包观察者时，在解密和回调结束后回收接收副本。观察者可以保留原始包，故该模式不回收已交付缓冲。解密输出继续独立持有，避免异步播放读取被覆盖的数据。
- 移除每100包重复输出的音频日志，保留5秒窗口统计、起始包信息及异常记录。
- 日志队列分普通、重要、关键三级，拥塞时优先淘汰最低级别记录。结束、错误和持续性能变化优先于普通连接事件。仍保持有界；全为关键记录时可能丢弃最旧关键记录，并单独累计 `droppedCritical`。
- 首次丢弃及此后最多每30秒输出累计丢弃分类，退出再次结算。概览保留前3个接收/处理窗口、首次加密采样、每分钟运行时快照和性能变化提示，减少分类轮转导致的早期证据缺失。
- 每条音频流附加进程内 `streamId`。最终 `Audio receive ended` 只在接收与解密两个线程均结束后输出，不等待或阻塞界面；包含 received、decrypted、decryptFailures、malformed、expired、overflow、cleanup 及 unaccounted。关闭后才提交的接收包计入 cleanup。
- 音视频解密每128次抽样一次，记录初始化、处理和认证结束阶段的线程CPU总耗时；首次和之后约30秒汇报。处理阶段包含输出分配、前缀复制及密文处理；这些是抽样总量，需按 samples 或 sealedBytes 归一化，不能当作全量解密耗时。
- 音频前3个有效5秒窗口建立CPU/字节基线；之后连续3个窗口达到基线1.8倍时，每流提示一次 `Runtime media cost-change`。这只表示相对变化，不是最终根因诊断；启动即慢的流可能不会触发。
- 后台采样尝试读取系统公开的ART GC计数、耗时及分配量。API17或OEM不提供时保留 unknown；不访问非公开运行时接口，也不把缺失值当0。

## 实车对照

使用相同设备、音频、动态画面和页面切换流程，持续至少40分钟。在前5分钟、10—15分钟及30分钟后重复相同操作，并导出整套日志。

重点比较平均解密CPU/包及CPU/字节、cost-change前后的分阶段CPU占比、接收过期/再缓冲、持续视频帧龄与输出量。核对最终 unaccounted=0、droppedCritical=0，以及起始窗口和分钟快照是否仍在概览。GC unavailable 时保留不确定性。

缓冲复用能减少分配，但不能据此宣称早间约2.6倍的解密成本变化已修复。若仍复现，应根据分阶段CPU变化决定后续是否比较其他加密实现。
