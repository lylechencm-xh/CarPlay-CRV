# 2026-10-28 后视镜摄像头切换修复记录

依据用户补充的主要复现场景及 `_carlogs/20261028/修复方案.md`，在现有 `.14` 工作区上增量修改。保留原有改动、版本号与音频期限；本轮未安装应用。

## 已实施

### 隐藏时立即解除旧视频队列的接收背压

原代码只在解密 worker 取出帧后检查 visibility epoch。若该 worker 正忙、接收队列已满，摄像头切入后 TCP 接收仍会等待队列腾空；隐藏降优先级也不会主动唤醒这次等待。

`ScreenReceiveQueue` 现在接收一致的 epoch/可见性状态，立即移除失效画面、释放相应字节预算并唤醒等待生产者。正在等待入队的旧帧即使随后切回也不会被重新归入新 epoch。配置消息保留原顺序，独立 AEAD nonce 仍在丢弃前推进；可见状态的正常帧继续按原容量背压，不任意丢压缩参考帧。

队列清理数计入原 hiddenSkippedTotal，作为隐藏画面跳过量，不计为网络丢包或音频过期。该修复消除一个已确认的切换背压缺口，尚不能证明它解释了全部音频丢弃。

### 隐藏通知先于音频服务操作

`setVideoVisible()` 先过滤重复状态，再发布隐藏状态并通知接收线程、安排视频清理。隐藏路径不再先获取音频管理锁，也不读取音频服务的路由快照；返回时仍保留必要的焦点恢复。音频播放队列、接收线程和传输会话不因画面隐藏而重建。

接收端有效可见性还加入 `videoReady`：Surface 清理旧解码器期间跳过图像解密，配置仍正常保留。Surface 状态改变也通知 visibility handler；清理线程等待隐藏通知发布后才能恢复 ready，再发布新 epoch 并请求关键帧。等待只发生在清理线程，回调在 videoLock 外执行，避免把同步等待或锁顺序反转带到页面线程。这样也覆盖 onResume 先于 Surface 创建的切回顺序。

### 切换与恢复现场留存

- 可见性事件附 sink、transition ID 与单调时间，进入关键日志与概览。
- 日志写入线程保存最近 30 秒、最多 96 条已有媒体摘要；切换时归档前窗，并捕获后 30 秒。快速切换合并，单次捕获最长 60 秒、最多 192 条归档，避免无界增长。该实现不在媒体线程写文件或采集额外系统快照。
- 归档带 capture、sourceEvent、sourceElapsedMs，原统计载荷保留流/TID。它是原事件的副本，不能再次加入包数、过期数或耗时分母；快速重复切换受限时，以原关键 transition 事件补充时间线。
- 视频恢复历史以 sink 为作用域保留最近 16 次，包含恢复事件号、实例、generation、计数、队列帧数、原因、处理结果。约每 60 秒及 sink 清理结束后重发，replay=true 表示历史副本。恢复 gate 抑制的请求不增加恢复事件。
- 以上留存仍受原诊断队列丢弃、文件轮转及应用异常终止限制。前窗只含已被写入线程收到的摘要；96 条不保证满 30 秒，后窗也不保证期间每个 worker 都有统计。不是逐包连续抓取。

### 渲染提交帧龄校准

输出选择器携带实际 buffer 的 PTS；只有 render=true 且释放成功才返回该 PTS，用于统计帧龄。恢复器仍使用同轮最大 PTS 判断进度。新字段 `renderAgeSchema=2` 区分口径，不与旧结果混算；无输出、不显示、无效时间和释放失败不增加渲染年龄。

源码复查时确认旧代码有 `newestOutputUs > 0` 防护，因此空轮询不会直接以 0 PTS 增加帧龄。此前方案把它列为待确认风险，本轮已澄清。实际修正的是同轮最大 PTS 与最终显示 buffer 不一致，以及释放成功之前就更新统计的边界；不能据此直接认定原 2877ms 峰值为误报。
