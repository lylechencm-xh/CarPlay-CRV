## 已修复的代码问题

### 尾帧恢复使用了错误的输入空闲时间

视频 PTS 保存的是完整消息到达应用的时间，不能当作向 codec 提交的时间。原 tailStalled 条件用 PTS 判断“4 秒没有新输入”，解密/队列延迟会使刚提交的尾帧被提前判为停顿。改用实际提交单调时间；4 秒阈值、750ms 持续观察和恢复 gate 保留。持续输入但不输出、严重积压和首次输出超时继续走原有恢复路径。

同一轮 drain 取出多个 buffer 时，使用其中最大 PTS 更新恢复器，避免最后取出的较旧 PTS 覆盖已观察到的新进度。恢复诊断包含全部非配置输出 buffer 数，覆盖被合并、不显示的旧输出；不把数量差直接解释为 codec 待输出帧数。

新增 decoder 实例编号、每条参考链的提交/输出计数、实际提交距今时间，以及同一媒体 sink 生命周期内跨实例累计恢复次数。tail stalled 与 output stalled 分别记录原因，便于核对报告中的三次恢复。

### iAP2 EOF 原因被丢失

`feedEof()` 现在明确记录 `iAP2 transport EOF`。协议 reset、重传超时等原始原因继续保留。终止事件在清理前附带状态、待确认/排队数量、待确认包的重传次数及下一期限；channel 附加最近成功读写和终止单调时间。不记录控制载荷或认证内容。

继续使用已有的单次释放、停止通知和重连机制，未叠加重试。新增 EOF、主动关闭、重复关闭测试，确认底层仅关闭一次，首次终止原因不会被清理覆盖。控制器新增 startIndex，与允许跳号的 epoch/attempt 区分。

## 为慢化定位补齐的诊断

- 解密阶段分为初始化、输出分配（含容量查询）、前缀复制、cipher process、认证结束、最终裁剪。schema=2 的 processCpuUs 只含 cipher 处理及计时边界开销，与旧 schema 的组合 process 不可直接混算。
- 汇报阶段 CPU 总量、密文字节、成功样本数、失败样本数、调用编号及单调区间。认证失败不混入成功耗时，后续调用可正常复用；未通过认证的明文仍不向消费者发布。
- 默认每个 128 次调用区间选一个可复现的变化位置，首次保留启动样本；记录模式和种子，减少固定位置抽样的代表性风险。另提供 fixed 和 off 对照。off 仅关闭阶段采样，现有全量解密计时和运行时快照仍保留。
- 音视频均有流标识与成本变化检测。音频前三个至少 100 包的有效窗口建立基线，视频前三个至少 1 帧的有效窗口建立基线；之后连续三窗达到 1.8 倍才告警，每流至多一次。视频内容/大小变化可能影响成本，这仍是排查提示，不能单凭告警定根因；启动即慢也可能无相对告警。
- 每个 worker 有界保存最近 24 个窗口，触发时通过原有异步日志队列归档前窗、触发窗及后续最多 24 个窗口。按原窗口时间回查；不足 24 窗或提前关闭时只保留实际存在的窗口，不把它们当作精确 120 秒连续覆盖。cost-window 进入概览和关键优先级，仍受队列及文件轮转上限约束。
- 普通启动阶段的完整 Snapshot 最多每 2 秒采集一次，跳过时记录 coalesced 原因。连接事件保持，失败和握手超时不受该限频影响。
- 播放队列分开累计 expired、capacity、byte-budget、oversized；同一包仅记一种原因，同时触发容量与字节预算时优先记容量，四项之和等于 droppedTotal。

### 实车采样对照入口

启动 Activity 时可传 `crypto_sampling=off|fixed|jittered`；未传或无效值使用 jittered。设置在 Activity 创建时生效，流创建时固定其模式。因 Activity 使用 singleTask，比较模式时需完整重启应用，不能只向已有界面追加启动参数。

示例（测试现场在允许重启应用时执行）：

```sh
adb shell am force-stop com.shihab.diplay
adb shell am start -n com.shihab.diplay/com.shilapi.xcertplay.CrvCarPlayActivity --es crypto_sampling off
```

fixed/jittered 使用同一入口。每场核对 `Runtime media sampling mode=`、crypto schema=2 的 sampling/seed、worker 及窗口时间；不要将三种模式的数据混在一个统计分母中。
